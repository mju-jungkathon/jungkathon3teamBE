# 회복 가이드 생성(`POST .../recovery-guide`) 500 에러 — 백엔드 로그 확인 요청

- 작성일: 2026-08-18
- 증상: 러닝 완료 후 화면 7(회복 가이드) 진입 시 `POST /running-sessions/{id}/recovery-guide`가 `500 Internal Server Error`를 반환. 가이드가 생성되지 않으니 뒤이은 `POST /running-sessions/{id}/complete`도 스펙대로 `404 E4040`(5.1을 건너뛴 것과 동일한 상태)으로 실패.

---

## 1. 재현된 세션

| sessionId | 증상 |
|---|---|
| `102d8dc0-05e7-4e63-98e4-364e8c906826` | `POST .../recovery-guide` → 500 |
| `4999f025-c9b5-49bd-8c8e-881467332eda` | `POST .../recovery-guide` → 500, 뒤이어 `POST .../complete` → 404 |

두 세션 모두 재현 시점의 프론트 요청 바디는 **빈 값**입니다(`recovery-guide`는 스펙상 body가 없는 API). 즉 클라이언트가 잘못된 값을 보내서 나는 에러가 아니라, **해당 세션이 DB에 들고 있는 데이터 상태에 따라 서버 내부에서 죽는 것**으로 보입니다.

## 2. 프론트에서 이미 확인·배제한 것

- **첫 번째 세션(`102d8dc0...`)**: 당시 프론트에 `run.lat`만 확인하고 `run.prepare`(UV 지수)는 기다리지 않는 레이스가 있어서, `POST /running-sessions`에 `uvIndexAtStart`가 `undefined`로(=필드 자체가 누락된 채로) 전송될 수 있었습니다. `5.1`의 "UV 노출량 = uvIndexAtStart × (durationSec/3600)" 계산이 `uvIndexAtStart`가 `null`일 때 NPE를 낼 가능성을 의심해 **이 레이스는 프론트에서 막았습니다**(CTA가 `prepare` 로딩 완료 전엔 비활성화).
- **두 번째 세션(`4999f025...`)**: 위 수정을 배포한 **이후**에도 동일하게 500이 재현됐습니다. 즉 `uvIndexAtStart` 누락만으로는 전체 원인이 설명되지 않습니다 — 같은 계산식에서 다른 값(예: `durationSec`가 비정상적으로 크거나 작은 값)이 문제일 수도 있고, 아예 다른 지점(심박수 조회부)일 수도 있습니다.
- **심박수 제출 타이밍**: rPPG 경로를 탄 세션이라면, 프론트는 `POST .../rppg/{id}/result` 응답을 받은 **이후에만** 사용자가 "솔루션 확인하기"를 눌러 화면 7로 넘어갈 수 있도록 순서를 강제해뒀습니다(측정 → 결과 제출 완료 대기 → 다음 버튼 활성화). 그래서 "프론트가 심박 제출을 기다리지 않고 너무 빨리 recovery-guide를 호출했다"는 시나리오는 아닐 가능성이 높습니다. 다만 **워치(WATCH) 경로**를 선택한 세션이라면 애초에 심박수 데이터가 하나도 없는 상태로 화면 7에 진입합니다(HealthKit은 웹에서 접근 불가라 워치 업로드 자체를 안 함 — 의도된 동작). `measuredBpm`이 `null`인 케이스에 대한 null 처리가 돼 있는지 확인 부탁드립니다.

## 3. 백엔드에 확인 요청

1. 위 두 `sessionId`로 애플리케이션 로그(스택트레이스) 확인 — 어느 지점에서 예외가 나는지가 가장 확실한 단서입니다.
2. `UV 노출량 = uvIndexAtStart × (durationSec / 3600)` 계산부에 `uvIndexAtStart` 또는 `durationSec`가 `null`/`0`일 때의 방어 코드가 있는지 확인.
3. 심박수 측정 이력이 0건인 세션(워치 선택 후 아무 업로드도 없는 경우)에서 `measuredBpm` 조회부가 `null`을 안전하게 처리하는지 확인.
4. 1순위 OpenAI 호출 실패 시 "조용히 규칙 기반(Mock) 생성기로 폴백"한다고 문서화돼 있는데, 폴백 로직 자체에서도 예외가 나는 경로가 있는지 확인(예: OpenAI가 5xx를 줬을 때 catch가 특정 예외 타입만 잡고 있어서 놓치는 케이스 등).
