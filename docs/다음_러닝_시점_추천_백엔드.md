# 🏃 다음 러닝 시점 추천 기능 — 백엔드 개발 문서

> 작성일: 2026-08-20
> 대상: AfterGrow 백엔드
> 관련 도메인: `recovery` (화면 7 — 회복 가이드)
> 목표: 회복 가이드 조회 시, 다음 러닝 추천 시점을 함께 제공

---

## 0. 기능 개요

**추천 로직 (규칙 기반, AI 미사용)**

```
추천 시점 = 회복 완료 예상 시각 이후 & UV 지수가 낮은 시간대
```

- 회복 완료 예상 시각 = `RecoveryGuide.created_at + cooldown_timer_sec`
- UV 낮은 시간대 = KMA 예보 데이터 중 향후 24~48시간 내 UV index 임계값 이하 구간

> ⚠️ 신규 테이블/마이그레이션 없음. 기존 `RECOVERY_GUIDES` 테이블과 기존 KMA 연동 클라이언트를 그대로 재사용.

---

## 1. 신규 엔드포인트

| 항목 | 내용 |
|---|---|
| Method | `GET` |
| Path | `/recovery-guides/{recoveryGuideId}/next-run-suggestion` |
| 인증 | 필요 (기존 JWT 인증 방식 그대로) |
| 신규 마이그레이션 | 없음 |
| 신규 외부 API 키 | 없음 (기존 KMA 키 재사용) |

**응답 예시 (성공)**

```json
{
  "success": true,
  "data": {
    "recommendedTime": "2026-08-21T07:00:00+09:00",
    "reason": "회복 완료 예상 시각 이후, UV 지수가 낮은 아침 시간대",
    "expectedUvIndex": 2
  },
  "error": null
}
```

**응답 예시 (추천 불가 — graceful degradation)**

```json
{
  "success": true,
  "data": {
    "recommendedTime": null,
    "reason": "UV 예보 데이터를 일시적으로 불러올 수 없어요. 회복 완료 후 다시 확인해주세요.",
    "expectedUvIndex": null
  },
  "error": null
}
```

> 프론트와 공유 시 이 응답 스펙(필드명)을 가장 먼저 확정해서 전달해야 프론트가 목업으로 UI를 병렬 개발할 수 있음.

---

## 2. 서비스 로직 (`RecoveryGuideService` 또는 신규 `RunSuggestionService`)

1. `recoveryGuideId`로 `RecoveryGuide` 조회
2. `cooldown_timer_sec` 존재 여부 확인 → 없으면 에러 코드 반환
3. 회복 완료 예상 시각 계산: `created_at + cooldown_timer_sec`
4. 기존 KMA 클라이언트로 향후 24~48시간 UV 예보 조회
5. 회복 완료 시각 이후 & UV 임계값(예: 3 이하) 이하인 첫 시간대 탐색
6. 조건에 맞는 시간대가 없으면 → `recommendedTime: null` + 안내 메시지로 fallback

---

## 3. 예외/엣지 케이스 처리

| 케이스 | 처리 방안 |
|---|---|
| `cooldown_timer_sec`이 null (R5 미완성 세션) | 신규 에러 코드 정의 (예: `E4041 - RECOVERY_NOT_READY`) |
| KMA API 호출 실패 | 500 에러 대신 `recommendedTime: null` + 안내 메시지로 degrade |
| 48시간 내 UV 낮은 구간 없음 | `recommendedTime: null` + "예보 범위 내 적합한 시간대 없음" 메시지 |
