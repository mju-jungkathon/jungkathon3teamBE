## 1. 애플리케이션 서버 — Spring Boot

- **역할**: 클라이언트 요청 처리, 비즈니스 로직, DB 연동을 담당하는 메인 API 서버
- **선택 이유**
    - 엔티티 관계(User – RunningSession – HeartRateMeasurement 등)가 명확한 도메인에 JPA/Hibernate가 잘 맞음
    - Spring Security로 인증/인가를 표준 패턴으로 구현 가능
    - AWS(ECS, RDS, Secrets Manager) 연동 레퍼런스가 풍부함
- **핵심 모듈**
    - `Spring Web` — REST API
    - `Spring Data JPA` — DB 매핑
    - `Spring Security` — 인증/인가
- **참고**: 실시간 폴링(`/live`) 트래픽이 커지면 Spring WebFlux(리액티브) 전환 또는 WebSocket/SSE 방식 고려

---

## 2. ORM — Spring Data JPA

- **역할**: 자바 객체(Entity)와 PostgreSQL 테이블을 자동으로 매핑해주는 ORM. SQL을 직접 안 짜도 CRUD 처리 가능
- **선택 이유**
    - 지난번 ERD의 `USERS`, `RUNNING_SESSIONS`, `HEART_RATE_MEASUREMENTS` 같은 테이블을 `@Entity` 클래스로 그대로 옮길 수 있음
    - `@OneToMany`, `@ManyToOne` 같은 어노테이션으로 FK 관계(예: RunningSession ↔ HeartRateMeasurement)를 코드로 명확하게 표현
    - Repository 인터페이스만 정의하면 기본 CRUD 메서드가 자동 생성됨 (`JpaRepository`)
- **예시**
    ```java
    @Entity
    @Table(name = "running_sessions")
    public class RunningSession {
        @Id @GeneratedValue(strategy = GenerationType.UUID)
        private UUID id;

        @ManyToOne
        @JoinColumn(name = "user_id")
        private User user;

        @OneToMany(mappedBy = "runningSession")
        private List<HeartRateMeasurement> measurements;
    }
    ```
- **주의할 점**
    - N+1 쿼리 문제: 연관 엔티티를 무심코 조회하면 쿼리가 폭증할 수 있음 → `fetch join`이나 `@EntityGraph`로 제어
    - 실시간 폴링처럼 성능이 민감한 구간은 JPA 대신 native query나 QueryDSL로 최적화하는 경우도 있음
    - 스키마 변경은 JPA의 `ddl-auto`에 맡기지 않고, 운영에서는 반드시 Flyway/Liquibase 같은 마이그레이션 툴로 버전 관리

---

## 3. 데이터베이스 — PostgreSQL (Amazon RDS)

- **역할**: 사용자, 러닝 세션, 심박수 측정 기록 등 영구 데이터 저장
- **선택 이유**
    - 트랜잭션/정합성이 중요한 관계형 데이터 구조
    - Multi-AZ로 장애 대응, 자동 백업/스냅샷
    - 필요 시 Aurora PostgreSQL로 전환해 읽기 복제본 확장 가능
- **연결 방식**: Spring Boot → JPA → JDBC → (운영 시) RDS Proxy 경유

---

## 4. 캐시 — Redis (Amazon ElastiCache)

- **역할**: 자주 조회/갱신되는 일시적 데이터를 메모리에 저장해 응답 속도 개선
- **사용처**
    - Refresh Token 저장 및 즉시 무효화 (로그아웃 시)
    - 러닝 세션 실시간 폴링(`/live`) 응답 캐싱
    - API Rate Limiting
- **판단 기준**: "서버 재시작으로 사라져도 괜찮은 데이터인가?" → 괜찮으면 Redis, 안 괜찮으면 PostgreSQL
- **도입 시점**: MVP 단계에서는 생략 가능. 폴링 부하나 토큰 관리 이슈가 실제로 생기면 도입

---

## 5. 인증 — JWT (Access Token + Refresh Token)

- **구조**
    - Access Token: 수명 짧음(15분~1시간), 매 API 요청 인증에 사용
    - Refresh Token: 수명 김(몇 주~몇 달), Access Token 재발급용, Redis에 저장해 즉시 무효화 가능
- **엔드포인트**
    - `POST /auth/signup`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`
- **보안 포인트**
    - 비밀번호는 BCrypt로 해시 저장
    - Refresh Token은 서버 측(Redis)에도 저장해 로그아웃/탈취 시 즉시 무효화
    - 클라이언트(React Native)는 토큰을 `react-native-keychain` 등 보안 저장소에 보관

---

## 6. 컨테이너화 — Docker

- **역할**: 애플리케이션과 실행 환경을 하나의 이미지로 패키징해 로컬-운영 환경 일치
- **구성 파일**
    - `Dockerfile` — 멀티스테이지 빌드(빌드용 이미지 + 경량 JRE 실행 이미지)
    - `docker-compose.yml` — 로컬에서 API 서버 + PostgreSQL + Redis 동시 실행

---

## 7. CI/CD — GitHub Actions

- **역할**: `main` 브랜치 push 감지 → 테스트 → Docker 빌드 → ECR 푸시 → ECS 배포까지 자동 실행
- **파이프라인 순서**
    1. 테스트 실행
    2. Docker 이미지 빌드
    3. Amazon ECR에 이미지 푸시
    4. Amazon ECS 서비스 업데이트 (무중단 롤링 배포)
- **인증**: GitHub ↔ AWS 연결은 장기 액세스 키보다 **OIDC 방식** 권장

## 8. 배포 인프라 — AWS

### 8.1 Amazon ECS (Fargate)
- 서버리스 컨테이너 실행 환경. 트래픽에 따라 자동 스케일링, 인스턴스 직접 관리 불필요

### 8.2 Amazon ECR
- Docker 이미지 저장소. GitHub Actions가 빌드한 이미지를 여기 푸시하면 ECS가 가져다 실행

### 8.3 ALB (Application Load Balancer)
- 클라이언트 요청의 최초 진입점. HTTPS 종료 후 ECS 컨테이너로 부하 분산

### 8.4 VPC
- 퍼블릭 서브넷(ALB) / 프라이빗 서브넷(ECS, RDS, Redis)으로 분리해 DB를 외부에 노출하지 않음

### 8.5 Secrets Manager
- DB 비밀번호, JWT 서명 키 등 민감 정보를 코드에 하드코딩하지 않고 런타임에 주입

### 8.6 CloudWatch
- 로그 수집, 에러율·응답시간 모니터링, 알람 설정

### 8.7 Route53 + ACM
- 도메인 연결 및 HTTPS 인증서 발급

## 9. (참고) 프론트엔드 연동 지점

> 아래는 백엔드 스택이 아니라, 프론트엔드(React Native)와 맞물리는 부분 중 백엔드 설계에 영향을 주는 것만 참고용으로 정리한 항목입니다.

- 클라이언트는 REST API로 통신하며 서버 코드와 독립적으로 개발·배포됨
- 애플 헬스(HealthKit) 연동은 클라이언트 네이티브 모듈이 처리 — 백엔드는 `GET /integrations/apple-health/heart-rate` 등으로 결과값만 수신
- 토큰은 클라이언트가 보안 저장소(Keychain)에 보관 — 백엔드는 토큰 발급/검증/무효화 로직만 책임짐
